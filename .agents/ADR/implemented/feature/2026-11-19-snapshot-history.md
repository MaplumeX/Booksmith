# ADR: Snapshot history for books

Status: implemented

Superseded in part by: [page-level snapshots](2026-11-19-page-level-snapshots.md) — 粒度与保留策略已被取代；
时间轴呈现、破坏性确认文案与「否决命名快照」的结论仍然有效。

## Problem

> 以下描述的是本次改造之前的实现状态。


右栏的「版本」tab 把一次保存的整包结果当作一个版本，列表是 `v1 / v2 / v3 · 2.1 MB · 3 天前`，唯一可做的动作是「恢复此版本」。这与使用者对「版本」的预期不一致：他们要的是笔记、文档软件里的历史快照——按时间组织的、能打开看一眼的、能退回的。当前实现是备份，不是历史。

三处能力建好了但没接通，是这个错配的症状：

- `note` 列（`apps/server/src/db/schema.ts`）在恢复时被写入 `restored from vN`，但 `FileStore.list()` 不查询它，`VersionDto` 没有这个字段，界面无法区分「保存产生的快照」和「恢复产生的快照」。
- `pinned` 列、`FileStore.markPinned()`、`prune()` 里的保留例外逻辑全部实现完毕，但**全代码库没有调用者**——没有 API 路由，没有按钮。它保护的正是「修个错别字也占一版」时会被挤掉的那一版。
- `sha256` 传到前端，没有被任何逻辑使用。

另外两条是行为缺陷而非呈现问题：

- 恢复会静默丢弃未保存的改动。`VersionsPanel` 不知道编辑器的 `dirty` 状态，点「确认恢复」后走 `onRestored()` → `Editor.reload()`，而 `reload()` 用 `new Map(loaded.texts)` 覆盖全部文本并 `setDirty(new Set())`。确认框只说「确认恢复」。
- 恢复粒度是整包。校对场景里最常见的是「第 5 章改坏了」，现在只能退回到整本书的某个时刻。

## Decision

**定位：文档级快照。** 一本书是一个文档，一个快照是这个文档在某个时刻的完整状态。使用者不需要知道 EPUB 内部有 28 个 xhtml 文件。

**主轴是时间，不是版本号。** 快照列表按天分组（今天 / 昨天 / 更早的具体日期），行内显示 `14:23` 与体积。`v3` 降级为 `title` 属性——它只是 `If-Match` 的乐观锁编号，不是产品概念。

**产生时机：保存。** 快照仍然只在你按下「保存」时产生，不引入定时器。

**不提供命名快照，`pinned` 一并删除。** 使用者明确否决了「给某个快照起名字」。`pinned` 列、`markPinned()` 与 `prune()` 的保留例外逻辑本来就没有调用者，否决命名后更不会有人接通，因此连列带代码一起删掉（迁移 `0002` 的 `DROP COLUMN`）。留一个永远为 false 的列只会让后来读者以为存在命名能力。

**保留策略改为时间稀疏化。** 最近 `RECENT_KEEP = 10` 个无条件保留；更早的按 UTC 日期分组，每组只保留 `versionNo` 最大的一个；总数上限 `TOTAL_CAP = 40`。

**表面：全屏浮层，不是侧栏 tab。** 版本从 `SIDEBAR_TABS` 移除。它是低频、任务型、需要大面积的操作，和常驻的「预览」抢同一个 440px 槽位本身是错位。入口用顶栏那个已经是纯文本的 `v{version}`，改成可点击的按钮，不新增控件。

**恢复语义：破坏性动作必须说清代价。** 有未保存改动时，确认文案写明「编辑器里 N 处未保存的改动将被丢弃」。不阻断（那会卡住「我有改动但想先看一眼旧版」这个正常动作），也不自动先存一版（那会为兜底吃掉一个紧张的版本槽位）。

## Alternatives considered

**编辑静默 60 秒自动生成快照。** 最接近笔记软件的心智，顺带解决忘记保存导致的改动丢失。但本项目每次快照是 2.1 MB 整包写入 Postgres `bytea`：一次三小时的编辑约产生 50 次快照，即 105 MB / 会话 / 本书，写入量涨两个数量级。使用者选择保持「保存时产生」，快照产品的价值 80% 来自「时间轴 + 能预览 + 能保住」，这三点不需要付这个存储代价。

**命名快照（接通 `pinned`，让用户给快照起名「投稿前」）。** 它几乎是零成本，且能直接解决「20 版上限挤掉重要版本」。使用者明确选择不做，接受「重要版本仍会被挤掉」这个后果；本记录把这一取舍写在这里，避免日后重新提出时以为是遗漏。

**撤销优先，把版本降为后台兜底，前台给深度撤销栈 + 自动草稿。** 它更贴近「我改错了想立刻退回一步」的真实动作，但推翻现有 `saving/dirty` 的保存模型，改动面最大。见 [the MVP decision](2026-11-19-epub-editor-mvp.md) 里已经落地的手动保存语义。

**恢复时自动先把当前改动存成一个快照。** 为兜底牺牲一个版本槽位，在 `TOTAL_CAP = 40` 下会挤掉真正的历史。

**有未保存改动时禁用恢复按钮。** 最安全，但把「我想先看一眼旧版再决定」这个正常操作卡死。

**只读预览放在右栏内嵌展开。** 侧栏 400–560px，渲染 xhtml 排版没有参考价值。

**只读预览让编辑器区接管为只读**（Google Docs 心智，曾被推荐）。使用者选择了全屏浮层，因为浮层能同时容纳「左时间轴 + 右 diff」，而编辑器区接管只能显示其中一半。

**单文件回退（只把 `ch005.xhtml` 退到某个快照）。** 它是校对场景里真实需要的能力，但属于文件级心智，与「文档级快照」的定位直接冲突，本版不做。

## Consequences

**验收结果（2026-11-19）**

- 顶栏的 `v{version}` 是按钮，打开全屏浮层；`SIDEBAR_TABS` 只剩「预览 / 查找 / 元数据 / 目录」。
- 浮层左栏按天分组（今天 / 昨天 / 具体日期），行内显示 `14:23` 与体积，当前版本带「当前」标记，`v{n}` 降为 `title`。
- 选中一条快照后右栏渲染该版与当前版的源码 diff；两版相同时显示「两版没有差异」。
- 只有非正文文件变化时显示「正文没有改动 / 这个快照只改了正文以外的文件：EPUB/content.opf」——实施中发现原先的空态会把这种情况误报成「两版没有差异」，已修正。
- 有未保存改动时确认文案为「编辑器里 N 处未保存的改动将被丢弃」，不阻断恢复。
- 恢复成功后内容等于目标快照，版本号递增（e2e `lists snapshots and restores an older one`，v2 → v3）。
- `prune` 在跨 10 天 / 25 个版本的构造数据上保留最近 10 个 + 每天最后一个 + 总数上限 40；`pinned` 列、`markPinned()` 与保留例外逻辑一并删除（迁移 `0002`）。

**代价与已知限制**

- 无命名机制之后，`TOTAL_CAP = 40` 会在大约 30 个编辑日之后开始丢旧快照。这是被明确接受的取舍；若使用者后来需要「钉住某一版」，本记录需要被新记录取代而不是就地修改。
- 时间分组用 UTC 日期，与使用者本地时区会有偏移；对「几天前」这个粒度的判断无影响，但如果将来要显示「昨晚 23:50」，分组需要改成服务器本地时区。
- 快照只在保存时产生，因此「忘了保存」导致的改动丢失不在本功能的覆盖范围内。
