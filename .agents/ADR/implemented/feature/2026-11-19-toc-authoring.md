# ADR: Authoring the table of contents

Status: implemented

## Problem

目录只能改名、上下移、删除。`apps/web/src/ui/TocPanel.tsx` 的三组动作对应
`updateAt` / `moveAt` / `removeAt`，都是对已有 177 项的重排；`packages/core/src/nav.ts` 的
`writeNavToc` 已经支持任意嵌套的 `children`，但没有任何入口能创建条目或改变层级。

[MVP 决策](2026-11-19-epub-editor-mvp.md) 把「目录增项与层级调整」列入
未交付项：新增章节之后，用户必须去手改 `nav.xhtml` 与 `toc.ncx` 才能让它出现在目录里，而两处
都要改、都要保持嵌套一致，这是最容易改坏的地方。

## Decision

**两个动作，都写进同一棵 `TocEntry` 树。**

- **新增条目**：从 spine 的文件列表里选一个文件（也可以手填 `path#fragment`），输入标题，
  追加到选中条目之后（无选中则追加到末尾）。`href` 由所选文件与目标文件目录反算为相对路径。
- **缩进 / 取消缩进**：把条目降为前一个兄弟的最后一个子项，或升为父条目的下一个兄弟。这两个
  动作只改树的形状，不改 `href`。

两处目录（`nav.xhtml` 与 `toc.ncx`）继续走现有 `writeNavToc` / `writeNcxToc` 同步；`playOrder`
由 `writeNcxToc` 递增重排，条目 `rawHtml`（标题内联 MathML）原样保留。

**新增条目的标题默认取目标文件里第一个 `<h1>`–`<h3>` 的纯文本**，取不到再回退文件名。这让
「新增章节 → 加一条目录」不用手打标题，同时仍然是人的一次确认，不是自动生成整本目录。

## Alternatives considered

**从全文标题自动重建目录（扫描每个 spine 文档的 `h1/h2/h3`，按层级生成）。** 对 pandoc 生成的
书可能一次就对，但它会**重写全部 177 项**：现有的手工标题、内联 MathML、锚点 id、层级调整
全部被覆盖。这是一个「一键毁掉用户此前所有目录编辑」的按钮，风险与收益不成比例。若以后要做，
也应该是「新建目录」而不是「重建目录」。

**只允许新增，不允许层级调整。** 那么新增的条目只能落在顶层，一本三层结构的书永远补不出正确
形状。缩进只是把节点从一个数组挪到另一个数组，成本远低于新增。

**直接编辑 `nav.xhtml` 源码。** 编辑器本来就能打开它，这是现状。但用户要同时维护 NCX 的镜像，
而且手写嵌套 `<ol>` 很容易错一层。目录面板存在的意义就是替用户维持这两处的同步。

## Consequences

**交付实测（2026-11-19）**

- 树操作 18 个单测（insert / indent / outdent / move / remove / update）。
- 真实书 179 项往返无损；新增条目保存重载仍在，缩进 padding 8→22→8（4 条 e2e）。
- 空标题回退文件名，自动标题取目标文件第一个 `h1`–`h3`。

**已接受的代价**

- 层级操作在深层嵌套（三层、177 项）下的边界容易错：缩进只在有前一个兄弟时可用，取消缩进只在
  有父节点时可用。两个按钮的 `disabled` 条件必须与树形状同步，否则会出现「点了没反应」。
- 新增条目的 `href` 若指向不存在的文件，目录面板已有的「锚点失效」标记会显示出来，属于可接受
  的中间状态。
