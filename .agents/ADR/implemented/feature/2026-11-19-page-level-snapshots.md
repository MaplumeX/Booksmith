# ADR: Page-level snapshots replace whole-book versions

Status: implemented

## Problem

一个版本曾经就是一次保存的**整包**（`book_versions.bytes`，2.1MB），历史按时间组织成「这本书
在某时刻的样子」。校对时的真实动作不是「把整本书退回昨天」，而是「第 5 章刚才那版更好」——
整包粒度把 25 章绑在同一条时间线上，改一个字和重排全书占同一个版本槽。

三条现场事实让这个错配变成硬约束：

- 一次保存写 2.1MB `bytea`，`TOTAL_CAP = 40` 且按时间稀疏化。任何高频保存（例如自动保存）
  都会在几小时内把真实历史挤空。
- 服务端的 `ingestEpub`（`apps/server/src/epub/ingest.ts`）本来就解包并解析整包，**逐条目比
  对是免费的**：保存时按 entry 的字节比较就知道哪几个文件真的变了。
- 一个章节平均 84KB（2.1MB / 25 章），一条页面快照是整包的三十分之一。

使用者要求快照按页面各自记录，而不是一本书一个整包。这条要求同时解除了
[旧记录](2026-11-19-snapshot-history.md)中「单文件回退属于文件级心智，与文档级快照定位冲突」
的否决；定位换成页面级之后，那个否决失去前提。本记录取代该记录的**粒度与保留策略**，不改变
它关于时间轴呈现、破坏性确认文案、以及否决命名快照的结论。

## Decision

**粒度的单位是一个文本条目（zip entry）。** `packages/core/src/text.ts` 的 `hasPageHistory`
决定谁进历史：`xhtml` / `html` / `htm` / `css` / `opf` / `ncx` / `xml` / `svg` / `js` / `txt`，
排除 `mimetype` 与 `META-INF/`。二进制（图片、字体）不进历史：编辑器不能编辑它们，只能整文件
替换，历史价值最低。同一个文件的 extension 判定也被编辑器复用（`isTextEntry`），两者分开是因为
`META-INF/container.xml` 仍然可编辑，只是不该有历史。

**整本书那一层没有历史。** `book_files` 每本一行（`bytes` / `sha256` / `updated_at`），每次保存
原地覆盖；`books.current_version` 仍是 `ETag` 与乐观锁编号，语义不变。迁移 `0003` 建两张新表并
把 `version_no = current_version` 的整包搬进 `book_files`，`0004` 删除 `book_versions`。拆成两份
是因为 drizzle-kit 在「同时加表又删表」时会要求交互确认重命名，非 TTY 环境无法作答。（*更新：当前态存储与恢复路径已由 [entry-level book storage](../architecture/2026-11-20-entry-level-book-storage.md) 迁至 `book_entries` 表并移除 `book_files`，快照比对与单页恢复现直接基于 `book_entries` 完成，页面快照粒度、10 分钟窗口、剪枝与 UI 语义保持不变。*）

**保存时只记录真正变化的条目。** `apps/server/src/routes/books.ts` 的 `changedTextEntries` 拿上一份
整包与新整包逐条目比字节，变化的条目才可能写入 `page_versions`。迁移、恢复、导入都走同一条路径：
导入会为每个文本条目写一条基线快照（`POST /api/books`），否则历史只能从第一次编辑开始。

**保留策略按文件各自计算**：每个文件保留最近 10 条无条件，更早的按 UTC 日期每组只留一条，单文件
上限 100 条。剪枝在保存后执行（`prunePages`）。同一文件十分钟内的重复保存不新增行——该窗口属于
[自动保存记录](2026-11-19-autosave.md)，剪枝本身不认识时间窗口。

**恢复是单条目动作**：`POST /api/books/:id/page-versions/:id/restore` 把该快照的字节写回当前整包
对应路径 → 重新 `ingestEpub` 校验 → `putCurrent` → 为该路径落一条新快照 → `current_version + 1`。
不删历史。

**表面是一个文件一条时间轴，入口在文件树上。** 文件树的每个条目有右键菜单（`FileTree` 的
`.context-menu`），「版本历史」打开该文件的全屏浮层：左栏是它自己的按天分组的版本列表（时间 +
体积，最新一条带标记），右栏是选中版本与编辑器当前内容的源码 diff，附「恢复这一版」。没有跨文件
的汇总列表。顶栏的 `v{version}` 打开**当前打开文件**的历史，保留它是因为右键不是唯一的发现路径；
二进制与 `META-INF/` 条目的菜单项置灰，它们从来没有快照。浮层默认选中「上一个版本」而不是最新
一版——最新一版通常等于编辑器当前内容，否则一打开就是「这一版和现在相同」。

## Alternatives considered

**只给 spine 里的正文 xhtml 建历史。** 最贴近「页面」这个词的直觉，行数最少。但 `content.opf`、
`nav.xhtml`、`toc.ncx`、CSS 同样是会改坏的东西——取消整本历史之后，选它会让元数据与目录的
改动变成无历史的孤儿，改错只能靠撤销栈或重新编辑。

**所有条目都进历史，含图片与字体。** 语义最一致。但一条图片动辄 500KB，而编辑器对二进制
只能整文件替换，历史上限会被一张图的几次替换吃掉。

**保留「每天 1 条整包快照」作为整本回滚的保险。** 每天只多 2.1MB，能回答「把整本书退回
昨天」。使用者明确说不要一本书整个快照，而页面历史覆盖到 `content.opf` 之后，整本回滚只是
逐页恢复的集合操作，为它维护第二条写入路径与第二套剪枝不值得。

**保留现状：每次保存一条整包。** 与「拆分成页面快照」直接冲突，且自动保存会让 40 个名额在
一次会话内耗尽。

**每本 100 条总上限。** 存储最可控（约 8.4MB/本），也是本次规划最初的推荐。使用者选择每
文件 100 条：一本书里被反复打磨的往往就是那两三章，全局名额会让它们挤掉其它章的历史。代价
见 Consequences。

**每文件 100 条 + 每本总量上限的双层规则。** 名额公平性更好，但两套阈值叠加后剪枝逻辑需要
解释三层，收益不抵复杂度。

**条目级增量上传协议（只传变化的文件）。** 能省下每次 2.1MB 的上传。沿用
[架构记录](../architecture/2026-11-19-server-backed-epub-editor.md) 的判断：单实例、2MB 量级，
增量协议换不到任何当期收益。

**全屏浮层里按文件分组，一个入口看全书。** 本次交付的第一版就是它：左栏列出所有有历史的文件，
展开后显示各自的快照。使用者否决——那仍然是「一本书的清单」，而且每次要在一堆文件名里找当前
文件。改成文件树右键之后，入口即定位，浮层里只有一条时间轴。

## Consequences

**验收结果（2026-11-19）**

- 服务端 `apps/server/test/pageVersions.test.ts`：16 条通过——导入为每个文本条目写基线、改一章只
  多一行、内容未变不写行不升版本、十分钟窗口内不新增、`x-booksmith-checkpoint: manual` 绕过窗口、
  过期 `If-Match` 409 不动历史、列表/取文本/恢复/跨书 404。
- 存储层 7 条：整包单行原地覆盖、按路径取最新、`prunePages` 同日 120 条 → 10、跨日 150 条 → 100、
  文件之间互不影响。
- e2e `history.spec.ts` 4 条：右键入口、二进制条目置灰、单文件 diff、顶栏入口；`--repeat-each=3`
  12/12 通过。
- 迁移在空的 `.pgdata` 上执行，`0003` 的搬运语句在无数据时为空操作，`0004` 删除旧表未丢真实数据。

**代价与已知限制**

- **存储上限约 210MB/本**（100 条 × 25 文件 × 84KB），20 本书约 4GB。该数字是算术推演，未在真库
  上量测；使用者已知情并选择。
- **整本书一次性回滚的能力消失。** 只能逐页恢复。
- 迁移 `0003` / `0004` 不可逆，旧的整本历史永久丢弃。
- 删除文件不产生墓碑：被删掉的条目无法从历史里恢复。
- 单条目恢复与并发保存仍靠 `ETag`：两个标签页同时恢复不同条目时，后者收到 409。
- 两标签页「先后自动保存」的冲突横幅只由手动保存路径的 e2e 覆盖，未手工复核；
  用户验收时豁免（waived by user, 2026-11-19）。
